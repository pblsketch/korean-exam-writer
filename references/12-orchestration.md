# 12 · 오케스트레이션 — 역할 분업·핸드오프·통합·평가

문항 생성 전 과정을 **한 에이전트가 통짜로** 하지 않는다. **오케스트레이터**가 흐름을 지휘하고,
역할별 **서브에이전트**가 각자 맡은 산출물을 만들며, 오케스트레이터가 **통합·평가·게이트**한다.
생성자와 검증자를 분리하는 것이 이 설계의 핵심(자기 산출물을 자기가 통과시키지 못하게).

## 에이전트 구성
| 역할 | 책임 | 산출물(핸드오프) |
|---|---|---|
| **오케스트레이터** | 맥락 수집, 위임, 통합, 게이트, 교사와 소통. **직접 집필·검증 안 함** | 단계별 진행·결정 |
| **자료조사관 (Researcher)** | 글감 후보 제시, 원본 출처 확보·신뢰도 평가, 인용 가능한 근거 스니펫 수집 | `sources[]`{sourceId,title,url,text,신뢰도}, 주제 후보 |
| **지문 설계자 (Architect)** | 전개 방식·문단 뼈대·핵심 개념/관계·밑줄 계획·예상 유형 배분 설계 | `blueprint`(개요) |
| **지문 집필가 (Writer)** | 승인된 개요+근거로 지문 집필, 사실 문장마다 `sourceQuote`·밑줄 표지 | `passage`(문장 배열) |
| **사실 검증관 (Fact-Verifier)** | **적대적**으로 지문을 다시 읽어 근거 없는 사실·왜곡 탐지(H1/H2) | pass/fail + 문장별 이슈 |
| **문항 출제가 (Item-Writer)** | 유형 배분·인지 계약·근거 역할·오답 10종으로 문항 작성. 안티-복제 | `questions[]` |
| **문항 검토관 (Item-Reviewer)** | **적대적** 품질 검증(정답 유일성·지문밖지식·약한 오답·난이도 충족) | questionQualityChecks + pass/fail |
| **조립관 (Assembler)** | exam JSON 조립, `validate_exam.py` 기계 게이트, 조판(HTML/HWPX) | 최종 산출물 |

## 실행 형태 — 하이브리드(순차 파이프라인 + 병렬 팬아웃)
전 과정을 한 줄로만 흘리지 않는다. **의존성이 있는 곳은 순차, 서로 독립인 곳은 병렬**로 돈다.

- **순차(불가피)**: 지문이 없으면 문항을, 지문을 안 썼으면 사실 검증을 할 수 없다.
  자료조사 → 설계 → 집필 → 사실검증 → (문항) → 조립 의 큰 뼈대는 앞 결과에 의존하므로 순차다.
- **병렬(적극 활용)**:
  1. **자료조사 팬아웃**: 여러 출처를 동시에 수집·신뢰도 평가(각 출처 독립) → 팬인으로 `sources[]` 통합.
  2. **통합형 (가)/(나) 병렬 집필**: 두 글은 독립 완결이므로 집필가 2명이 동시에 쓴 뒤 통합(공통 비교축만 공유).
  3. **문항 팬아웃/팬인 ★ 최대 병렬 기회**: **지문이 확정되면 문항끼리는 서로 독립적**이다.
     유형 배분(`01`)으로 슬롯을 나눈 뒤 **문항별 출제가를 동시에 fan-out**하고, **검토관이 fan-in으로 모아**
     정답 유일성·유형 중복·약한 오답을 일괄 검증한다.

## 핸드오프 계약 (입력 → 출력)
1. 오케스트레이터 → **자료조사관(병렬)**: `context` → 여러 출처 동시 수집 → 팬인 `sources[]` + 주제 후보 3개
2. 오케스트레이터 → **설계자**: `context`+승인 주제+`sources[]` → `blueprint`
   - blueprint = { 주전개+보조전개(`11`), 문단별 기능(6~8개), 핵심 개념·관계, 밑줄 표지 계획(㉠~㉤), 유형 배분(`01`)·문항 슬롯 }
3. 오케스트레이터 → **집필가**: 승인된 `blueprint`+`sources[]` → `passage`(sid·text·factual·sourceQuote·markers)
   - 통합형이면 (가)·(나)를 **집필가 2명이 병렬 집필** 후 통합.
4. 오케스트레이터 → **사실 검증관**: `passage`+`sources[]` → 판정. **집필가의 논리를 신뢰하지 말고 원본으로부터 재확인.**
5. 오케스트레이터 → **출제가(팬아웃)**: 확정 `passage`+슬롯별 계약 → 문항을 **슬롯 단위로 동시 생성**
   (각 출제가에는 근거를 **역할·위치만** 전달, 원문 미제공) → 팬인 `questions[]`
6. 오케스트레이터 → **검토관(팬인 검증)**: `passage`+`questions[]` → 일괄 판정 (약한 오답 2개↑·유형 중복이면 해당 문항만 실패)
7. 오케스트레이터 → **조립관**: 확정 exam → `validate_exam.py`(exit 0 필수) → 조판

## 통합·평가·재작업 규칙
- **기계 게이트가 최종 심판**: 사람/에이전트 판정과 별개로 `validate_exam.py`가 축자 인용·근거 수·오답 반증을
  기계 검증한다. exit 0 아니면 조판 금지(주관적 "괜찮음"으로 통과 못 함).
- **재작업 루프(각 최대 2회)**: 사실 검증관 실패 → 집필가 재작성 / 문항 검토관 실패 → 출제가 재작성.
  반복 실패 시 해당 항목 제거 후 부족분을 교사에게 보고(날조 금지).
- **분리 원칙**: 같은 역할이 생성과 최종 검증을 겸하지 않는다. 오케스트레이터는 산출물을 만들지 않는다.

## 호스트별 실행
- **서브에이전트 지원(Claude Code 등)**: 오케스트레이터가 Task/Agent로 각 역할을 **별도 에이전트**로 위임하고
  핸드오프 산출물만 주고받는다(컨텍스트 격리 → 적대적 검증이 진짜 독립적).
  - **병렬 실행**: 자료조사·통합형 집필·문항 팬아웃은 `run_in_background: true`로 **동시 스폰** 후 팬인에서 결과를 모은다.
    (독립 작업만 병렬. 사실검증·조립처럼 앞 결과에 의존하는 단계는 순차.)
- **미지원(일반 ChatGPT 등)**: 단일 에이전트가 역할을 **순차 페르소나**로 전환해 수행한다. 병렬 팬아웃은
  "문항 5개를 한 번에 설계한 뒤 하나씩" 식의 **의사(擬似) 병렬**로 대체한다. 전환 시 "지금은 사실 검증관으로서
  앞 결과를 신뢰하지 않고 원본만 보고 검증한다"처럼 **역할·태도를 선언**해 분리 효과를 낸다.

## 교사 접점
각 단계 산출물은 오케스트레이터가 교사에게 제시하고 **승인/수정 체크포인트**를 거친다(→ `13-interactive-workflow.md`).
